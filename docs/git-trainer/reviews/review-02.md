## Дефекты: учат неправде

### 1. `git commit` на чистом дереве печатает вывод без строки `On branch <ветка>`

**Где:** `app/src/trainers/git/engine/branchCommands.ts`, `handleCommit`, строка 414:

```ts
if (sameTree(state.index, state.working)) return fail(state, 'nothing to commit, working tree clean', null)
return fail(state, formatBranchingStatus(state), null)
```

**Почему неверно.** У настоящего git «nothing to commit, working tree clean» — не отдельное сообщение, а **последняя строка полного длинного статуса**, который всегда начинается с `On branch <ветка>`. `builtin/commit.c`, `prepare_to_commit()`:

```c
if (!committable && whence != FROM_MERGE && !allow_empty && ...) {
    s->hints = advice_enabled(ADVICE_STATUS_HINTS);
    ...
    run_status(stdout, index_file, prefix, 0, s);
```

`run_status()` → `wt_status_print()` → `wt_longstatus_print()`, где `On branch %s` печатается в начале, а `nothing to commit, working tree clean` — в финальном `else` того же вывода (wt-status.c). То есть реальный вывод:

```
On branch master
nothing to commit, working tree clean
```

**Чем грозит.** Сразу в соседней ветке того же `if` (строка 415) движок печатает статус *с* заголовком. Игрок видит: грязное дерево → «On branch master» есть, чистое → заголовка нет. Он выучит, что это два разных по природе ответа git, тогда как это один и тот же статус. Отдельно замечу: комментарий в `repo.ts` (строки 491–499) сам документирует, что настоящий git печатает здесь две строки с `On branch`, — то есть раздел 2 воспроизвёл известную разделу 1 ошибку (`repo.ts:445` делает то же самое). Это не «как в разделе 1, значит норма»: это ошибка, размноженная копированием.

### 2. `git checkout <ветка>` печатает `A\t<файл>` для неотслеживаемого файла — git такой строки не печатает никогда

**Где:** `app/src/trainers/git/engine/branchRepo.ts`, `applyTreeChange`, строки 417–431 (в связке с `localChangeFiles`, 317–328, и `checkSafety`, 378: неотслеживаемый файл проходит как «не заблокирован» и попадает в `carried`):

```ts
const type: CarriedFile['type'] = !inResult && inNextWorking ? 'A' : inResult && !inNextWorking ? 'D' : 'M'
```

Для файла, которого нет ни в HEAD, ни в индексе (обычный неотслеживаемый файл), и которого нет в целевом дереве: `dirty` — да (`w !== idx`), блокировки нет (правильно), и он уезжает в `carried` с буквой `A`. Вывод команды становится `A\tnew.txt\nSwitched to branch 'dev'`.

**Почему неверно.** Этот отчёт у git — `show_local_changes()` → `run_diff_index(&rev, 0)` (builtin/checkout.c), то есть `diff --name-status` между **деревом новой ветки и индексом/рабочим деревом**. `run_diff_index` перебирает записи **индекса**; неотслеживаемых файлов там нет по построению — ровно как `git diff HEAD` никогда не показывает untracked. Сам комментарий в коде (строки 422–427) верно называет источник — `show_local_changes()`/`run_diff_index()`, — но условие написано по присутствию в *рабочем дереве*, а не в индексе, и поэтому захватывает untracked.

**Чем грозит.** Это самый вероятный сценарий миссии: игрок создаёт новый файл, переключает ветку — и получает выдуманную строку `A\t<файл>`. Он выучит, что checkout отчитывается о неотслеживаемых файлах (и что они «добавлены»), хотя git их в этом отчёте игнорирует. Условие `knownToGit` для этого уже посчитано в `checkSafety` — в `applyTreeChange` его аналога нет.

### 3. Конфликт «изменён/удалён» и «добавлен/добавлен» объясняется игроку как конфликт по строкам

**Где:** `handleMerge` в `branchCommands.ts`, строки 304–308 — единственная ветка отказа на *любой* конфликт из `mergeTrees`; текст в `app/src/trainers/git/locales/ru.ts`, строки 349–350:

> «настоящий git начал бы слияние веток «X» и текущей с конфликтом — **правки задели одни и те же строки одного файла**»

**Почему неверно.** `mergeTrees` (`branchRepo.ts`, 278–304) кладёт в `conflicts` не только построчные конфликты, но и:
* modify/delete — файл удалён в одной ветке и изменён в другой (`o === undefined`, `t !== b`);
* add/add — файл создан в обеих ветках с разным содержимым (`b === undefined`).

Ни в том, ни в другом случае «правки не задели одни и те же строки одного файла» — в первом случае строк вообще нет с одной стороны. У настоящего git это отдельные классы конфликта с отдельными сообщениями (`CONFLICT (modify/delete)`, `CONFLICT (add/add)`), и учебно они важнее строчного: игрок, которому сказали «вы задели одни и те же строки», будет искать пересечение строк там, где его нет. Побочно тот же текст не совсем точен и для соприкасающихся правок (правки на *соседних* строках, а не на одних и тех же) — это верно по git, но формулировка вводит в заблуждение.

### 4. `checkSafety`: заявленное правило «git не проверяет совпадение содержимого» неверно для индекса

**Где:** `branchRepo.ts`, `checkSafety`, комментарий 362–368 и реализация 370–386:

> «git отказывает по файлу, только если a) операция реально меняет его содержимое относительно текущего HEAD, И b) в этом файле есть локальная правка (staged или unstaged) — **независимо от того, совпадает ли итоговое содержимое случайно с локальной правкой** (git не проверяет совпадение… — подтверждено прямым экспериментом)».

**Почему неверно.** `unpack-trees.c`, `twoway_merge()` — дословно:

```c
} else if ((!oldtree && !newtree) || /* 4 and 5 */
     (!oldtree && newtree && same(current, newtree)) || /* 6 and 7 */
     (oldtree && newtree && same(oldtree, newtree)) || /* 14 and 15 */
     (oldtree && newtree &&
      !same(oldtree, newtree) && /* 18 and 19 */
      same(current, newtree))) {
    return keep_entry(current, o);
}
```

Случай 18/19: дерево цели отличается от HEAD, но **запись индекса уже совпадает с целевым содержимым** → `keep_entry`, никакой ошибки. То есть если игрок сделал `git add` правки, которая случайно совпала с версией в целевой ветке, настоящий git переключится, а движок откажет. Для *незастейджённой* правки утверждение движка верно (там срабатывает `verify_uptodate`, сравнивающий рабочее дерево с индексом, а не с целью) — видимо, эксперимент был именно на ней, а вывод обобщён на оба случая.

**Чем грозит.** Практически случай редкий, но в коде он зафиксирован как *общее правило* с пометкой «подтверждено прямым экспериментом» — а такие пометки живут дольше кода и расходятся по следующим шагам. Это же правило применяется и к fast-forward-ветке `handleMerge` (строка 268).

### 5. Подсказка в блоке «Changes not staged for commit» не меняется при удалениях

**Где:** `branchRepo.ts`, `formatBranchingStatus`, строки 529–540 — всегда печатается `  (use "git add <file>..." to update what will be committed)`.

**Почему неверно.** `wt-status.c`, `wt_longstatus_print_dirty_header()`: при `has_deleted` печатается `  (use "git add/rm <file>..." to update what will be committed)`, иначе — вариант без `/rm`. Модель раздела 2 умеет незастейджённые удаления (`notStaged` c типом `deleted`, строка 486), так что случай достижим: удалить файл из рабочего дерева без `git add` и вызвать `git commit -m …`.

Здесь же, в блоке `Changes to be committed:` (строки 521–528) вовсе нет подсказки, тогда как git печатает `  (use "git restore --staged <file>..." to unstage)` (wt-status.c, `wt_longstatus_print_cached_header()`). Сегодня этот блок недостижим (в `handleCommit` статус печатается только при `index == HEAD`), поэтому это пока не видимая игроку неправда — но код «наполовину настоящий», и первый же, кто подключит `formatBranchingStatus` к `git status` раздела 2, получит усечённый вывод, не заметив этого. Отмечу, что комментарий (строки 505–511) объясняет расхождение с `repo.ts` только по блоку «Changes not staged» и про этот пропуск молчит.

## Мешает работе

### 6. `git checkout <файл>` для файла со staged-удалением тихо «восстанавливает» его

**Где:** `branchCommands.ts`, строки 199–206: `knownPaths` собирается из **HEAD ∪ индекс**.

У настоящего git `git checkout -- <path>` восстанавливает из **индекса**, и pathspec сопоставляется с записями индекса; путь, который есть в HEAD, но убран из индекса (`git rm --cached` / застейджённое удаление), под pathspec не попадает, и git отвечает `error: pathspec '<путь>' did not match any file(s) known to git` (pathspec.c, `report_path_error()`, вызывается из `checkout_paths()`). Движок вместо этого выдаёт `Updated 0 paths from the index`. Уверенность средняя: это я вывел из логики `checkout_paths`/`report_path_error`, дословной цитаты условия сопоставления с индексом я не получил — проверьте прогоном, когда будет git.

### 7. Неоднозначность «имя ветки или имя файла» разрешается молча в пользу ветки

**Где:** `branchCommands.ts`, 193–207: сначала `state.branches`, потом путь.

Настоящий git в этом случае не выбирает, а останавливается: `die(_("'%s' could be both a local file and a tracking branch.\nPlease use -- (and optionally --no-guess) to disambiguate"))` (builtin/checkout.c, `parse_branchname_arg()`). Для миссий шага A маловероятно (нужен файл с именем ветки), но если такая миссия появится, тренажёр научит, что git молча предпочитает ветку.

## Замечания

8. **Diffstat опущен везде** — после `commit` (`[master abc1234] msg`), после `Fast-forward` и после `Merge made by the 'ort' strategy.` настоящий git печатает ` file | 1 +` / `1 file changed, …`. В разделе 1 это задокументированное упрощение (`repo.ts`, 161–169); в разделе 2 такого объяснения в коде нет, хотя упрощение то же. Стоит хотя бы сослаться на него в шапке `branchCommands.ts`, иначе следующий правящий решит, что это недосмотр, и начнёт «дорисовывать» статистику по неполной модели.

9. **Два разных `git status` в одном тренажёре.** Раздел 1 печатает один хинт в «Changes not staged», раздел 2 — два. Расхождение осознанное и задокументировано (`branchRepo.ts`, 505–511), но для игрока, проходящего разделы подряд, это выглядит как нестабильность вывода git. Либо выравнивать, либо принимать сознательно — но это цена дублирования форматтера, и она уже начала набегать (см. также находки 1 и 5).

10. **`FileMergeResult.content` при `conflict: true` содержит `ours`** (`branchRepo.ts`, 235) — значение бессмысленное, но типом не отличимое от валидного. Сейчас никто его не читает; при следующей правке (шаг B, разрешение конфликтов) это готовая ловушка. Лучше `content: null` при конфликте.

11. **`mergeBase` — BFS «первый встреченный предок»** (`branchRepo.ts`, 91–104). Ограничение честно описано в комментарии и для историй шага A корректно. Оговорюсь: при появлении коммитов слияния в миссиях (а шаг A их создаёт!) BFS может вернуть не «лучшую» базу в крест-накрест истории. На простых сценариях, включая «слили, потом снова разошлись», я проверил вручную — результат совпадает с git. Но если шаг B добавит повторные слияния, это место придётся пересматривать.

12. Мелочь: `branchTypes.ts`, строка 16 — «однoветочной» написано со смешанной кириллицей/латиницей (`o` латинская). То же в тестах: `branchCommands.test.ts`, строки 165, 244 — «meняет», «незакоммiченными» (латинская `i`) в 89, 104. Поиск по коду по этим словам работать не будет.

## Что я проверил и признал верным (в том числе на предмет регресса после первого круга)

Эти места я разбирал прицельно, потому что их правили, и расхождений с git не нашёл:

* **Правило независимости ханков** (`hunksOverlap`, `branchRepo.ts`:177). `xdiff/xmerge.c`, главный цикл `xdl_merge`: `if (xscr1->i1 + xscr1->chg1 < xscr2->i1) { независимы }` и симметрично для второй стороны — строгое `<`. Отрицание этого ровно равно `h1.bStart <= h2.bEnd && h2.bStart <= h1.bEnd`. Правка `<` → `<=` **корректна**, соприкасающиеся правки и разные вставки в одну точку у git действительно конфликт. Регресса в обратную сторону нет: я прогнал по формулам десяток конфигураций (вставка против замены, вставка против вставки, правки через одну строку), результат движка и формула git совпадают во всех.
* **Распознавание «обе стороны сделали одну и ту же правку»** (`sameRange && arraysEqual`, строка 229). У git — `xscr1->i1 != xscr2->i1 || xscr1->chg1 != xscr2->chg1 || xscr1->chg2 != xscr2->chg2 || xdl_merge_cmp_lines(...)` → конфликт; то есть совпадение требует того же начала, той же длины в базе и того же содержимого. Это в точности условие движка. Уровень слияния у `git merge` — `XDL_MERGE_ZEALOUS` (ll-merge), не `MINIMAL`, так что ветка сравнения включена.
* **Отказ `git merge` при непустом индексе и его дословный текст** (`indexDiffersFromHead` + `handleMerge`, 290–297). `merge-ort-wrappers.c`, `unclean()`: `error(_("Your local changes to the following files would be overwritten by merge:\n  %s"), sb.buf)`, вызывается первой строкой `merge_ort_nonrecursive()`/`merge_ort_recursive()` и возвращает -1; дальше `builtin/merge.c` печатает `Merge with strategy %s failed.`. Формат «два пробела + пути через пробел одной строкой» — это `repo_index_has_changes()`, которая складывает пути в strbuf через пробел. Проверка действительно идёт **до** вычисления слияния и до обнаружения конфликта. Размещение в движке (после «Already up to date.», после fast-forward, до `mergeTrees`) совпадает с порядком в `cmd_merge`.
* **Fast-forward при непустом индексе разрешён.** `t/t6424-merge-unrelated-index-changes.sh`: тест «ff update» вызывает `git merge E^0` **без** `test_must_fail` и проверяет, что застейджённый посторонний файл уцелел; не-перемоточные тесты («resolve, trivial», «resolve, non-trivial», «recursive») — под `test_must_fail` с ожиданием «changes to the following files would be overwritten». Поведение движка (checkSafety для FF, полный отказ для не-FF) этому соответствует.
* **`git checkout -b <имя>` на грязном дереве НЕ печатает `M\t<файл>`** — комментарий движка (branchCommands.ts, 172–182) верен, я проверил цепочку целиком: `builtin/checkout.c`, `cmd_checkout()`: `if (argc == 3 && !strcmp(argv[1], "-b"))` с комментарием «User ran 'git checkout -b <branch>' and expects the same behavior as 'git switch -c <branch>'» → `only_merge_on_switching_branches = 1`; в `switch_branches()`: внутри `if (!new_branch_info->name) { … if (opts->only_merge_on_switching_branches) do_merge = 0; }` → `merge_working_tree()` и вместе с ней `show_local_changes()` не вызываются. Для формы с начальной точкой (`argc == 4`) правило другое — движок её и не принимает.
* **Порядок «M\t<файл>» перед заголовком** — `show_local_changes()` вызывается в конце `merge_working_tree()`, а заголовок печатает `update_refs_for_switch()`, вызываемая в `switch_branches()` после неё. Порядок в движке верный.
* **Буква `D` для локально удалённого файла** — `show_local_changes()` диффит **новый коммит** против рабочего дерева (`show_local_changes(&new_branch_info->commit->object, …)`), так что сравнение с результирующим деревом, как в движке, правильное (кроме случая untracked — находка 2).
* **Все сообщения `git branch -d/-D`** сверены с `builtin/branch.c`: `branch '%s' not found` (без точки), `cannot delete branch '%s' used by worktree at '%s'`, `the branch '%s' is not fully merged` + `If you are sure you want to delete it, run 'git branch -D %s'` через `advise_if_enabled` (что даёт вторую строку `hint: Disable this message with "git config set advice.forceDeleteBranch false"`), `Deleted branch %s (was %s).`, `branch name required`. Совпадает дословно. «Merged» относительно текущего HEAD — `branch_merged()` берёт `head_rev`, если нет upstream; у движка так же.
* **`Merge branch 'x'` vs `… into develop`** — подавление `into` для `main`/`master` по умолчанию (fmt-merge-msg, `merge.suppressDest`); поведение движка верное.
* **Раскладка блоков `git status`** (пустая строка между блоками, но не после `On branch`, выравнивание меток на 12 колонок) — соответствует `wt_longstatus_print_trailer()` и ширине меток в `wt-status.c`.
* **`merge: <имя> - not something we can merge`** (`help_unknown_ref`, без префикса `fatal:`), **`fatal: No remote for the current branch.`** (`setup_with_upstream`), **`Nothing specified, nothing added.` + два hint и код возврата 0** (builtin/add.c), **`Updated N path(s) from the index` с подсчётом только реально изменённых путей** (`checkout_paths`, `nr_checkouts` не увеличивается для неизменившихся файлов) — верно.
* **`mergeTrees`** по всем комбинациям add/delete/modify: удаление против «не менялось», добавление с одной стороны, одинаковое содержимое с обеих — разобраны вручную, совпадают со стандартным трёхсторонним правилом.

Итог: правки первого круга по существу сделаны корректно, новых расхождений в тех местах, что правились, я не нашёл — все четыре «учит неправде» из моего списка находятся в местах, которых первый круг не касался (пункты 1, 2, 5) либо касался частично и обобщил вывод шире, чем позволяет git (пункт 4).
