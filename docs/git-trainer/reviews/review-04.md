## А. Учит неправде

### A1. `git commit` без -m и `git commit -m ""` на чистом дереве: движок пишет «Aborting…», а git показывает статус
Файл `branchCommands.ts:483` и `:487`. Проверки пустого сообщения стоят раньше проверки «нечего коммитить» (`:507`). У настоящего git порядок обратный: сначала «нечего коммитить», и до редактора дело не доходит.
```
$ git commit -m ""            # чистое дерево
On branch master
nothing to commit, working tree clean
rc=1
$ GIT_EDITOR=true git commit  # чистое дерево
On branch master
nothing to commit, working tree clean
$ echo x>f; GIT_EDITOR=true git commit   # есть только незастейдженная правка
On branch master
Changes not staged for commit:
...
no changes added to commit (use "git add" and/or "git commit -a")
$ git commit -m ""            # то же дерево
(тот же статус), rc=1
```
Движок в этих случаях отвечает `Aborting commit due to empty commit message.`. Для формы без -m он добавляет пояснение `ru.explain.commitAborting`: мол, git открыл бы редактор. На чистом дереве это неправда, потому что git редактор не открывает. Игрок усвоит, что без сообщения git «спотыкается о редактор», хотя на деле ему просто нечего коммитить. Тесты `branchCommands.test.ts:731–752` проверяют только случай, где есть застейдженные изменения. Для них ответ верный, а ошибочный порядок тестами не покрыт.

### A2. Слияние при двух общих предках (история «крест-накрест»): движок сообщает о конфликте, git сливает без конфликта
Файл `branchRepo.ts:106–107`, `mergeBase` возвращает `best[0]`. Комментарий признаёт, что такие истории вне шага, но движок не отказывает честно, а считает результат. Потом `branchCommands.ts:374` выводит `ru.branching.errors.mergeConflictOutOfScope`: «настоящий git начал бы слияние … с конфликтом: в файле «…» правки задели одни и те же строки». Такую историю можно собрать только командами из шага A (branch/checkout/commit/merge):
```
root: f=x, g=y
master: A1 (f=a); git branch tmpA
b:      B1 (g=b); git branch tmpB
master: git merge tmpB  -> M1
b:      git merge tmpA  -> M2
master: A2 (f=a2);  b: B2 (g=b2)
$ git merge-base --all master b
e4f90ae…   (A1)
faf0269…   (B1)
$ git merge b
Merge made by the 'ort' strategy.
rc=0         f=a2, g=b2
```
В движке лучших общих предков два, A1 и B1. От A1 файл g идёт в конфликт (y→b против y→b2), от B1 файл f (x→a2 против x→a). Какой бы предок ни выбрал `best[0]`, движок заявит о конфликте, которого у git нет. Правильно было бы при `best.length > 1` отказать честно: «такая история вне шага».

## Б. Мелкие неточности (тоже неправда, но редкая или косметическая)

### Б1. Движок принимает имена веток, которые git отвергает
Файл `branchCommands.ts:68–70`, функция `isInvalidBranchName` знает четыре правила. Все остальные имена движок молча создаёт с `ok`. Git 2.53.0 отвечает на каждое из них `fatal: '<имя>' is not a valid branch name` + hint, rc=128. Проверенные имена: `a~b`, `a:b`, `foo.lock`, `foo/`, `foo.`, `.foo`, `/foo`, `a//b`, `a@{b`. Комментарий называет эти правила «вне области», но отказа по правилу области нет: движок ведёт себя так, будто git эти имена принимает. Для сравнения: `head` и `@` git действительно принимает (rc=0), тут движок прав.

### Б2. Любой выдуманный флаг объявляется «настоящей возможностью git»
Файл `branchCommands.ts:128–129`, `:235–236`, `:295`, `:413`, `:476`. Сюда попадает любой аргумент с `-`, и игрок видит `optionOutOfScope`: «… — настоящая возможность git, но этот шаг тренажёра её не разбирает». Настоящий git на выдуманные флаги отвечает так:
```
$ git branch -foo        -> error: unknown switch `o'  + usage, rc=129
$ git merge --bogus      -> error: unknown option `bogus'
$ git checkout -zzz      -> error: unknown switch `z'
$ git commit --bogus     -> error: unknown option `bogus' + usage, rc=129
```
Опечатка вроде `--amned` получает от тренажёра подтверждение, что такая опция есть. Комментарий на `:136–138` сам фиксирует ответ git «unknown switch», а текст для игрока говорит обратное.

### Б3. Сообщение коммита не очищается от пробелов
Файл `branchCommands.ts:466`, `:473`. Отбрасывается только строго пустое значение.
```
$ git commit -m "   "          -> Aborting commit due to empty commit message. rc=1
$ git commit -m " " -m x       -> [master f994d7f] x      (%B = "x\n\n")
```
Движок на первую команду создаст коммит с сообщением из пробелов. На вторую напечатает первым абзацем `" "`, а должен `x`. Сценарий редкий.

## Что проверено и совпало с git 2.53.0
- **Имя ветки:** «пробел», `..`, `HEAD`, `head` (принят); `branch -foo` → unknown switch; `checkout -b -foo` → ошибка имени; `checkout -b 'a b' master` → ошибка имени раньше разбора начальной точки; `checkout -b` → `` error: switch `b' requires a value ``; `branch -d`/`-D` без имени → `fatal: branch name required`; `a branch named … already exists`.
- **checkSafety и перенос правок при checkout, 15 случаев.** Незастейдженная правка при смене файла целью, в том числе когда правка случайно равна цели, → отказ. Застейдженный файл, совпавший с целью, с правкой поверх → проходит и печатает `M\tf`. Застейдженное значение, не совпавшее с целью, → отказ. Файл, удалённый через `rm`, на затронутом пути → проходит, файл восстанавливается версией цели. `git rm` на затронутом пути → отказ. `git rm` при файле, удалённом в цели → проходит молча. Неотслеживаемый файл, совпадающий с целью или отличающийся от неё, → отказ. Застейдженный новый файл, отличающийся от цели → отказ; совпадающий → молча; а если в цели его нет → `A\tn`. Правка или удаление постороннего файла → `M\tkeep` / `D\tkeep`. Строки отчёта идут перед `Switched to…` и `Already on…` (проверено через stdbuf). `checkout -b` на грязном дереве печатает только заголовок.
- **Вывод двух блоков ошибки** (modified + untracked, один `Aborting`) совпал дословно для checkout, для fast-forward merge (после `Updating …`) и для настоящего слияния (перед `Merge with strategy ort failed.`).
- **Порядок проверок в merge:** `Already up to date.` при грязном индексе; fast-forward при застейдженном постороннем файле проходит; настоящее слияние при застейдженном постороннем файле → формат `  g h new` одной строкой, rc=2; проверка индекса идёт раньше проверки неотслеживаемых; грязный файл на конфликтном пути даёт ошибку перезаписи, а не конфликт; `merge` без аргументов → `No remote…`; `nope - not something we can merge`.
- **Построчное слияние, 9 случаев:** правки через одну строку сливаются без конфликта; соседние правки, вставка рядом с правкой, удаление рядом с правкой, «надмножество» одинаковой правки, дописывание разного в конец, первая и последняя строки двухстрочного файла дают CONFLICT; одинаковая вставка схлопывается. Строка `Auto-merging` печатается только при настоящем построчном слиянии.
- **Сообщение коммита слияния:** `into develop` для develop, без `into` для master и main.
- **Склейка нескольких -m:** `-m a -m "" -m b` → `a\n\nb`, итоговая строка `[master …] a`; `-mfoo`; `` switch `m' requires a value ``; на чистом и на грязном незастейдженном дереве при заданном -m выводится полный статус.
- **Прочее:** `branch -d` для слитой, неслитой, текущей и несуществующей ветки; `-D`; порядок в списке веток (`B2`, `a`, `b1`, `master`); `add` без аргументов, с несуществующим путём, для удалённого файла; `checkout <неизвестное>` → pathspec-ошибка.
