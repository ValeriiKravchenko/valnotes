## Что сделано по каждому пункту задачи

**1. Исходное состояние.** `createInspectSection(seed)` строит цепочку коммитов из
`seed.commits` (сообщение+дерево на коммит, интегратор задаёт бизнес-контент — index.html/
style.css нигде не зашиты в движке) и принимает отдельно `index`/`working` для сценария
«index.html изменён и не подготовлен, style.css изменён и подготовлен» (часть V). В тестах
использован ровно тот сценарий, что описан в target.md.

**2. Команды.**
- `log`: голый, `-n <N>`/`-<N>` (в т.ч. `-n2`), `--oneline`, одна ссылка, `A..B`, `<файл>`,
  `-- <файл>`.
- `diff`: голый, `--staged`/`--cached`, `HEAD`, `<коммит>`, `A B`, `A..B`, `<файл>`,
  `-- <файл>`, `--stat`, `--name-only`.
- `show`: голый и с одной ссылкой.
- `status -s`/`--short` (и голый `status` — решение ниже, в «упрощениях/решениях»).
- Ссылки: `HEAD`, `HEAD^`, `HEAD~N`, `HEAD~~`, имя ветки, начало хэша от 4 символов, `X@{0}`
  (частный случай) — `resolveRef` в `inspectRepo.ts`.

**3. Вывод diff — настоящий формат.** `inspectDiff.ts` строит `diff --git a/… b/…`,
`new file mode 100644`/`deleted file mode 100644`, `--- /dev/null`/`+++ /dev/null`,
`index a..b [100644]`, `@@ -старт,счёт +старт,счёт @@` (с омитированием `,1`, сверено
напрямую). Нигде нет «(файла не было)» или подобных придуманных строк.

**4. Автор и дата.** `commit <id>\n\n    <сообщение>` — без `Author:`/`Date:` (проверено тестом
явно). Пояснение об этом — в `ru.inspecting.ui.noAuthorDateNote` (текст теоретической рамки,
не привязан к конкретной команде).

**5. Что НЕ входит — по правилу области.** `inspectScope.ts` + `inspectCommands.ts`:
три ответа (в области / реальная возможность, здесь не разбирается / не существует в git).
`log --graph/--stat/-p/--author/--since`, `diff -w`, `status -sb`, `blame`, диапазон `A...B`,
`HEAD^2`, `HEAD~3` (за пределами корня), `HEAD@{N}` (N≠0) — всё это даёт честный отказ, а не
имитацию. `git init/add/branch/checkout/merge/commit` — настоящие команды, не реализованные
здесь (второй ответ), `git stauts`/`git foobar` — третий ответ (`is not a git command`).

**6. Четыре миссии по событию.** `inspectMissions.ts`: `log` (голый `git log`), `logOneline`
(`git log --oneline`), `diff` (голый `git diff`), `diffStaged` (`--staged`/`--cached`) —
засчитываются по факту успешной команды именно этой формы в `state.history`, «однажды true —
навсегда true».

## Тексты, сверенные с git (git 2.53.0, mktemp-каталог, 26.09.2026)

- `git log`/`git log --oneline`/`-n`/`-N` (в т.ч. `-n` без числа → `error: -n requires an
  argument`; `-n abc` → `fatal: 'abc': not an integer` — это уточняет формулировку spec.md
  S3-04, которая обобщённо говорит «без числа» → «not an integer»: реально «not an integer»
  относится к нечисловому значению, а к полностью отсутствующему — другое сообщение; в движке
  разведены оба случая правильно).
- `git log HEAD^/HEAD~2/HEAD~3` (ambiguous argument, ровно два случая, включая точный текст с
  подсказкой про `--`).
- `git log <файл>` vs `git log -- <файл>` (историю по правкам файла).
- `git log --oneline HEAD~2..HEAD`.
- `git diff`/`--staged`/`--cached`/`HEAD`/`<коммит>`/`A B`/`A..B`/`<файл>`/`-- <файл>`/
  `--stat`/`--name-only` — все формы прогнаны напрямую, включая:
  - точный формат `diff --git`/`index`/`---`/`+++`/`@@` для модификации, нового и удалённого
    файла (в т.ч. что у нового/удалённого файла на `index`-строке НЕТ хвостового режима, а у
    обычной модификации — есть);
  - омитирование `,1` в счётчике хунка;
  - формат `--stat` (полоса `+`/`-`, выравнивание столбца имён, единственное/множественное
    число `file(s)`/`insertion(s)`/`deletion(s)`);
  - что `git diff -- <несуществующий_или_неотслеживаемый_файл>` — это ПУСТОЙ вывод с кодом 0, а
    не ошибка (проверено отдельно и для `log`, и для `diff`);
  - что `git diff --staged HEAD~1` (одна ревизия) — валидная форма у настоящего git (индекс vs
    указанный коммит), а `--staged <A> <B>` (две) — `usage`-отказ; первую форму раздел 3
    сознательно не реализует (см. «Упрощения», п. 6), вторую — воспроизводит как отказ.
- `git show`/`git show <ссылка>` (в т.ч. корневой коммит: файлы как `new file mode`, не
  «(файла не было)»).
- `git status -s`/`--short` — формат `" M"/"M "/"MM"/"??"`, тот же, что уже проверен в разделе 1
  (`repo.ts`, `formatStatusShort`) — переиспользован тот же формат (не импорт кода, а
  независимая реализация под `InspectState`, по правилам проекта).
- Разбор ссылок: `HEAD^`, `HEAD~`, `HEAD~~`, `HEAD^^`, `HEAD~1^`, `<ветка>~1`, короткий хэш от
  4 символов, `HEAD^2`/`HEAD~3`(за пределами корня)/`HEAD@{99}`/`abc` (не найдено), `HEAD@{0}`
  (тот же коммит) — все семь/четыре/один случай из spec S3-41…S3-43 сверены напрямую
  (`git rev-parse`).
- `git diff -- untracked.txt` (явный pathspec на неотслеживаемый файл) — пустой вывод, код 0 —
  проверено отдельно уже в процессе работы (это и вскрыло ошибку, см. ниже).

## Найденная и исправленная ошибка модели (до сдачи)

Первая версия `diffBetween` сравнивала два дерева чисто структурно и поэтому показывала
неотслеживаемый файл (например `todo.txt`, есть в `working`, нет в индексе) как «новый файл» в
`git diff`/`git diff HEAD` — прямое нарушение target.md, часть V, «опасное место 2»
(«Неотслеживаемые файлы в git diff не видны»). Тест S3-28 поймал это. Исправлено функцией
`trackedWorking` (`inspectRepo.ts`): везде, где правой стороной сравнения выступает само рабочее
дерево, оно предварительно ограничивается файлами, известными git (есть в индексе) — то самое
различие «есть на диске» / «известен git» из A12 (часть II), примененное здесь к diff, а не к
pathspec коммита. Проверено дополнительно прогоном настоящего git (`git diff --
untracked.txt` → пустой вывод, код 0) — модель теперь соответствует.

## Список упрощений (для ревью)

1. **Хэш блоба на строке `index a..b [mode]`** — не настоящий SHA1 (нет полноценного
   объектного формата git), а тот же приём, что и для id коммита (target.md, A5):
   детерминированный хэш от содержимого, 7 hex-символов. Формат строки настоящий, конкретное
   значение — нет. Явно закомментировано в `inspectDiff.ts`.
2. **Режим файла всегда `100644`** — исполняемый бит не моделируется (в разделе нет способа
   его выставить).
3. **Маркер `\ No newline at end of file` не печатается никогда.** Контент файлов тренажёра —
   обычная JS-строка без соглашения о завершающем `\n`; признака «файл не заканчивается
   переводом строки» в этой модели не существует как отдельное данное. Указано явно в
   `inspectDiff.ts`.
4. **«Контекст функции» в заголовке хунка** (`@@ … @@ <текст>`, эвристика xdiff, показывающая
   последнюю подходящую строку перед хунком, — у настоящего git есть даже для не-C файлов)
   НЕ воспроизводится. Прогоном подтверждено: у всех диффов зафиксированного сценария раздела 3
   (короткие файлы, хунк с первой строки) эта эвристика не срабатывает вовсе — проверено
   отдельно на длинном синтетическом файле (эвристика подтверждена как реальное поведение git),
   но не реализована, так как не нужна текущему сценарию. Если содержимое раздела в будущем
   станет длиннее и хунк окажется не с первой строки, этот пробел станет видимым.
5. **`--stat` без масштабирования полосы по ширине терминала.** Настоящий git ужимает полосу
   `+`/`-` у больших диффов, чтобы вписаться в 80 столбцов; файлы тренажёра короткие, порог не
   достигается ни в одном сценарии раздела — не реализовано.
6. **`git diff --staged <одна ревизия>`** (например `git diff --staged HEAD~1`) — настоящая
   форма git (индекс vs указанный коммит, а не HEAD), подтверждённая прогоном, но НЕ входит в
   таблицу «Что входит» target.md (там только голый `--staged` и `--staged <файл>`) —
   сознательно не реализована, ответ «второй» (реальная возможность, здесь не разбирается), а
   не попытка угадать точное поведение без явного требования.
7. **Классификация опций — точным совпадением, без разбора сокращений и кластеров коротких
   флагов** (в отличие от `branchScope.ts`/`classifySection2Option` раздела 2). Единственное
   явное исключение — литерал `-sb` (S3-35), добавленный отдельной строкой, потому что тест
   spec.md называет именно эту форму; другие кластеры с `-s` (например `-sz`) этим списком не
   покрыты и correctness для них не гарантирована. Названо явно как более строгий, а не более
   снисходительный, тренажёр (при сомнении отказывает, не выдумывает).
8. **Списки `REAL_GIT_COMMANDS`/`SECTION3_REAL_OPTIONS` не исчерпывающие** (тот же принцип, что
   и в разделах 1–2, target.md A10) — покрывают явно названное в target.md/spec.md и соседние
   распространённые опции тех же команд, не более.
9. **`git diff A B`/`git diff <ref> -- <файл>` и подобные композиции ref+pathspec, не
   протестированные напрямую** — реализованы через общие для log/diff примитивы
   (`resolveRefOrRange`, `diffBetween(…, files)`), которые по отдельности сверены с git; сама
   композиция логически прямая, но не прогонялась целиком как отдельный сценарий.
10. **Неоднозначный короткий хэш (несколько коммитов с общим префиксом)** трактуется так же,
    как «не найдено» (`null`), а не отдельным сообщением `short SHA1 … is ambiguous` (настоящий
    git разводит эти два случая текстом). При 3 коммитах и 7-значном хэше коллизия практически
    недостижима — риск принят, как и в разделе 2 (`branchRepo.ts`, `mergeBase`, похожий класс
    решений).
11. **Голый `git status` (без `-s`) реализован**, хотя target.md, «Что входит» для раздела 3
    называет явно только `-s`/`--short`. Решение: раздел 2 уже реализует голый `status`
    (`formatBranchingStatus`), отключать уже известную, реальную и безобидную форму без явного
    запрета показалось user-hostile упрощением ради упрощения — при сомнении рискнул в сторону
    «работает как настоящий git», а не искусственного отказа. **Это решение стоит сверить с
    ревьюером/интегратором** — если раздел должен фокусироваться СТРОГО на коротком формате,
    голый `status` легко убрать (одна строка в `inspectCommands.ts`, `handleStatus`).
