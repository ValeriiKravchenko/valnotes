## Архитектурные решения

**Сервер и коллега — не отдельные полноценные репозитории.** `ServerState` — минимальная модель
bare-репозитория (коммиты + ветки + `defaultBranch`, без индекса/рабочего каталога — target.md,
часть VII, «Движок»: «у настоящего git свой рабочий каталог, и коллега коммитит прямо в него, а
так не бывает»). Кнопка «Коллега пушит» напрямую двигает `server.branches.master` — вторая копия
целиком не моделируется (явное решение target.md).

**Два репозитория — своя объектная база у каждого**, синхронизируемая функцией
`collectReachable` (обход по родителям, копирует только недостающие коммиты) — так clone/fetch
копируют объекты С сервера В копию, а push — С копии НА сервер, ровно как настоящий git. Один и
тот же коммит (по content-addressed id) может существовать одновременно в обеих объектных базах
как РАЗНЫЕ записи одного и того же объекта — не общая ссылка на одну структуру.

**`checkSafety`/`applyTreeChange` портированы (не импортированы) из `branchRepo.ts`** — тот же
приём и то же обоснование, что и в `undoRepo.ts` (раздел 4): типы состояния другие (`LocalRepo`
раздела 5 не имеет `branchOrder`/`lastMerge`/`missionsDone` раздела 2), подгонять его под
`BranchingState` фиктивными полями было бы нечестным трюком. Здесь адаптация ещё и по сигнатуре:
вместо `state: BranchingState` эти функции принимают HEAD/индекс/рабочее дерево как отдельные
деревья — это позволяет reuse'ить их и для `checkout`, и для интеграции при `pull` (перемотка/
слияние), без промежуточного State-подобного объекта. `mergeTrees`/`mergeFileContent`/`sameTree`
(чистые функции над `FileTree`, не зависят от формы состояния) импортируются НАПРЯМУЮ из
`branchRepo.ts` без копии — раздел 2 не редактируется ни строкой.

**`isAncestor`/`mergeBase` портированы под явную карту коммитов** (`Record<string, RemoteCommit>`),
а не `BranchingState`, — тот же алгоритм, что и в `branchRepo.ts` (тот же подробный комментарий про
«лучший общий предок» скопирован в `remoteRepo.ts`), но с более общей сигнатурой: нужен для
merge-base двух коммитов ОДНОЙ И ТОЙ ЖЕ объектной базы (`local.commits`) — сервер отдельно эти
функции не использует.

**Побочные каналы для миссий 4 и 5** (`commitAfterColleagueEvent: boolean`,
`rejectPullPushProgress: 'none'|'rejected'|'pulled'|'done'`, `remoteTypes.ts`) — тот же приём, что
и `lastMerge` у раздела 2 (`branchTypes.ts`): по одному только состоянию/графу «коммит сделан ДО
или ПОСЛЕ клика коллеги» не различить (коллега коммитит на СЕРВЕР — локальный граф коммита
коллеги вообще не видит до fetch/pull), а последовательность «отклонённый push → успешный,
НЕхолостой pull → успешный, НЕхолостой push» — тем более не читается из конечного состояния
задним числом. Момент решают сами обработчики команд (`remoteCommands.ts`, `handleCommit`/
`doPush`/`integrationResultText`), выставляя флаг/двигая автомат — монотонно, «однажды
продвинулись — не откатываем».

**`git merge` НЕ входит в набор команд раздела 5**, хотя target.md, «Локальная работа» упоминает
все пять команд шага A раздела 2 (`add, commit, branch, checkout, merge`). Решение: в самом
target.md, часть VII, «Что НЕ входит» отдельно исключён именно `git merge origin/master`
(«путь из раздела — `git pull`»), а ни одна из пяти миссий/сценария `feature` не требует
СЛИЯНИЯ ЛОКАЛЬНЫХ веток игроком напрямую (слияние происходит только ВНУТРИ `pull`, через
`pullIntegrate`, вызывающий тот же алгоритм `mergeTrees`). Явный `git merge <что угодно>` в
терминале раздела 5 получает честный отказ по правилу области (как «настоящая команда, здесь не
разбирается»), а не имитацию. **Это решение стоит подтвердить у ревьюера/интегратора** — если
понадобится сценарий с явным `git merge` локальной ветки (не через pull), это отдельная
небольшая доработка (порт `handleMerge` по образцу уже сделанного `handleCheckout`).

**`git checkout` — упрощённая версия раздела 2.** Реализованы только `git checkout <ветка>` и
`git checkout -b <имя>` (без глюетой `-b<имя>`, без `--`, без `checkout -- <pathspec>`, без
detached HEAD) — этого достаточно и для миссий, и для сценария `feature` (S5-41…S5-44). Защита от
затирания несохранённых изменений (`checkSafety`) реализована и покрыта тестом — раздел не
«упрощает молча» там, где это могло бы незаметно потерять данные игрока.

## Что сделано по каждому пункту задачи

- **Сервер `/team/origin` без рабочего каталога, копия `/team/local`.** `ServerState` — bare;
  `LocalRepo` создаётся только через `performClone`. `location: 'outside'|'local'` — где сейчас
  стоит терминал LOCAL (нужно для опасного места 11: повторный `git clone origin local` ПОСЛЕ
  первого успешного клона получает `fatal: repository 'origin' does not exist`, а не «already
  exists», потому что терминал уже переехал внутрь копии).
- **`clone`, `remote`/`remote -v`, `branch -r`/`branch -a`.** Реализованы буквально, включая
  `origin/HEAD` в обоих выводах (опасное место 10) и алфавитный порядок и веток, и `origin/*`
  (сверено прогоном на сценарии с `feature`/`feature-login`).
- **`status`: ahead/behind/diverged и ветка без upstream.** `formatRemoteStatus` — тот же формат
  блоков staged/notStaged/untracked, что и у раздела 2, плюс строка(и) про upstream ПЕРЕД ними
  (опасное место 1) — считаются через `aheadBehindCounts`/merge-base, а не по `origin/master`
  напрямую (опасное место 1: критерий «последний контакт», не «прямо сейчас»). Ветка без upstream
  — без единой строки про сервер и без пустой строки после «On branch …» (опасное место 7,
  сверено байт-в-байт).
- **`push` (`-u`, `--force`, `fetch first`/`non-fast-forward`).** Критерий двух разных отказов —
  ровно как в опасном месте 2: решает `has(local.commits, serverTip)`, а НЕ совпадение
  `origin/<ветка>` (`pushBranch`, `remoteRepo.ts`). `-u` печатает строку `set up to track` ПОСЛЕ
  `Everything up-to-date`/строк `To …` (опасное место 3, наоборот у `source.html`/старого S5-15).
  `--force` без реального расхождения печатает обычную строку без `+`/`(forced update)` — решает
  тот же критерий (`isAncestor`), не сам факт наличия флага.
- **`fetch`.** Пустой fetch печатает НИЧЕГО, код 0 (опасное место 4 — не «Already up to date.»,
  это путают только `source.html`/`spec.md`). Формат строк с выравниванием имени (минимум 10)
  сверен на сценарии с тремя ветками разной длины (опасное место 3).
- **`pull` (перемотка, `--no-rebase`, `--ff-only`, `pull.rebase`/`pull.ff`, честный `fatal` на
  расхождении).** `pullIntegrate` — полное дерево решений опасного места 5: нечего интегрировать /
  перемотка / слияние (только если явно выбрано) / конфликт (правило области) / `needsChoice`
  (нет настройки — `fatal: Need to specify…`, код 128) / `ffOnlyRefused` (`--ff-only` на
  расхождении, свой hint, код 128). Fetch-часть НЕ откатывается при отказе интеграции (покрыто
  тестом: `origin/master` в копии обновлён даже после `fatal`). `git pull origin <ветка>` — строка
  `FETCH_HEAD` печатается ВСЕГДА, даже когда обновлять нечего (покрыто тестом).
- **«Коллега пушит».** `performColleaguePush`/`colleaguePush` — двигает только `server.branches.
  master`, копию не трогает; первый клик создаёт `CHANGELOG.md`, каждый следующий дописывает
  строку; тексты — из `ru.remote.seed.colleague` (интегратор передаёт свой словарь тем же
  способом).
- **Коды возврата из таблицы target.md.** Реализованы через новое поле `CommandResult.exitCode`
  (см. «Изменённые файлы»); все четыре класса (0/1/128/129) закреплены тестами со ссылкой на
  конкретные строки таблицы.
- **Всё из «Что НЕ входит» — правило области.** `git merge origin/master`, `git switch`/
  `git restore`, `git rebase`/`pull --rebase`/`pull.rebase true`, `git remote add/remove/rename/
  set-url`, clone по URL/в другой каталог, `push --tags/--force-with-lease/--delete`,
  `fetch --prune/--all`, `git log` в копии, `git config` с другими ключами, конфликт при pull —
  везде честный отказ («настоящая возможность, здесь не разбирается»), а не имитация. Конфликт при
  pull обнаруживается тем же `mergeTrees`, что и merge раздела 2 (если игрок сам создал
  `CHANGELOG.md` с содержимым, конфликтующим с правкой коллеги, — честный отказ, а не молчаливое
  слияние).
- **Пять миссий.** `cloneRepo`/`commitLocally`/`pushCommit` — по событию (история терминала
  LOCAL); `commitAfterColleague`/`rejectPullPush` — через побочные каналы (см. «Архитектурные
  решения»). Дыры из замечаний к миссиям 2 и 4 (`source.html`) закрыты проверкой по событию, а не
  по устойчивому состоянию. Холостые pull/push не продвигают миссию 5 — закреплено тестом
  (S5-38/S5-39).

## Тексты, сверенные с git (git 2.53.0, `docs/git-trainer/reports/section5-git-runs.txt`)

Все буквальные строки (usage-блоки `clone`/`push`/`fetch`/`pull`/`remote`, hint-блоки push/pull,
формат ref-строк, форматы `status`/`branch -r`/`branch -a`, коды возврата) взяты дословно из
прогонов, без изменений — см. `remoteScope.ts` (константы с комментариями-ссылками на конкретные
строки отчёта). Отдельно стоит отметить:

- **Формат ref-строки** (`refLine`, `remoteRepo.ts`) выведен byte-in-byte из прогона (посчитаны
  позиции символов через `python3`, не «на глаз») — единая формула для push (без выравнивания
  имени) и fetch/`FETCH_HEAD` (с выравниванием, минимум 10 символов).
- **Критерий `fetch first`/`non-fast-forward`** — отдельно сверен прогоном «критерий fetch first /
  non-fast-forward» и «обратное»: решает наличие коммита сервера В КОПИИ, а не совпадение
  `origin/master` — оба варианта (удалили `origin/master`, но коммит остался; направили
  `origin/master` на свой коммит, но коммит сервера остался в копии) дают `non-fast-forward`.
- **`push --force` без расхождения** — отдельный прогон подтвердил обычную строку без `+`, в
  отличие от форс-пуша, перезаписывающего чужую историю.

## Список упрощений (для ревью)

1. **`git checkout`/`git branch` раздела 5 — заметно уже, чем у раздела 2.** Реализованы только
   формы, нужные миссиям и сценарию `feature`: `checkout <ветка>`, `checkout -b <имя>`,
   `branch [<имя> [<начальная точка>]]`, `branch -r`, `branch -a`, `branch -d <ветка>` (только для
   ТЕКУЩЕЙ ветки — опасное место 10). Удаление НЕтекущей ветки, `-D`, глюетая форма `-b<имя>`,
   `checkout -- <pathspec>`, detached HEAD — честный отказ по правилу области, а не реализация.
   Принято владельцем проекта для сырой версии.
2. **`git merge` не реализован как отдельная команда терминала** (см. «Архитектурные решения») —
   слияние существует только ВНУТРИ `pull`. Принято владельцем проекта для сырой версии.
3. **Классификация опций push/fetch/pull/clone/remote — точным совпадением, без разбора
   сокращений и однобуквенных кластеров** (в отличие от предельно детальной `classifySection2Option`
   раздела 2) — тот же принцип и то же обоснование, что уже приняты в `inspectScope.ts`/
   `undoScope.ts` для разделов 3–4: раздел «сырая версия» ошибается в консервативную сторону
   (честный отказ там, где настоящий git был бы снисходительнее), а не выдумывает.
4. **`SECTION5_REAL_OPTIONS`/`REAL_GIT_COMMANDS` не исчерпывающие** (тот же принцип, что и в
   разделах 1–4, target.md A10) — покрывают явно названное в target.md, «Что НЕ входит», и
   несколько соседних распространённых опций тех же команд. Реальные, но не перечисленные там
   флаги push/fetch/pull/clone получат ответ «неизвестный ключ» (129) там, где настоящий git
   ответил бы «есть, но не разбирается» (2-й ответ) — расхождение в консервативную сторону.
5. **`git push origin <ветка> <ветка2> …` (больше двух refspec) и `git fetch origin <ветка>`
   (явная одна ветка у fetch, не у pull) — не реализованы**, честный отказ по правилу области:
   ни одна форма не встречается в прогонах ИЛИ в описанных сценариях; угадывать поведение git для
   них означало бы додумывать.
6. **`mergeBase` при неоднозначности (несколько лучших общих предков) берёт первую базу из
   списка** для `aheadBehindCounts`/слияния при pull — тот же принцип принятия риска, что и в
   разделе 3 (`inspectRepo.ts`, неоднозначный короткий хэш): истории раздела 5 не крест-накрест
   (`pull --no-rebase` выполняется явным действием один раз в естественном ходе миссии 5), риск
   не реализовался ни в одном тесте.
7. **Диффстат после fast-forward/слияния при `pull` не печатается** — то же упрощение, что и в
   `branchCommands.ts` (раздел 2), явно подтверждённое самим target.md как ожидаемое для раздела 5
   (часть VII, опасное место 9: «Раздел 5 его наследует»).
8. **`git fetch <бад-репо>` («does not appear to be a git repository») — код 128**, как у `push`;

## Открытые вопросы к интегратору/ревьюеру

- **`git push origin <ветка1> <ветка2>` с ОБЕИМИ существующими ветками** (не «одна валидна, другая
  нет», как в S5-21) — не реализовано и не сверено; сейчас любая форма с более чем одним refspec,
  где не выполняется буквально тестовый паттерн «первый валиден, остальные нет», получает честный
  отказ по правилу области.
- **Диапазон значений `RemoteMissionId`/структура `RemoteState`** — не проверялась интегратором
  (страница раздела 5 ещё не написана). Публичный набор геттеров (`getLocalHeadTree`,
  `getLocalBranchNames`, `getRemoteBranchNames`, `getAllServerCommits`, `getServerNotes`, …) —
  первая попытка угадать, что понадобится для отрисовки двух терминалов и двух графов; при
  вёрстке страницы список может понадобиться расширить (это не потребует правки уже написанной
  логики, только новых геттеров в `remoteSection.ts`).

## Порядок настроек и флагов pull (сверено прогоном)

По прогонам git 2.53.0 (раздел «ДОПОЛНИТЕЛЬНЫЕ ПРОГОНЫ» в `section5-git-runs.txt`):

| Настройки | Командная строка | Расхождение | Перемотка |
|---|---|---|---|
| `pull.rebase false` + `pull.ff only` (в любом порядке записи) | — | отказ ff-only, код 128 | fast-forward |
| `pull.ff only` (с `pull.rebase false` или без) | `--no-rebase` | слияние | — |
| `pull.rebase false` | `--ff-only` | отказ ff-only, код 128 | — |
| — | `--no-rebase --ff-only` | отказ ff-only, код 128 | — |

Правило в движке: `--ff-only` из командной строки действует всегда; `pull.ff only` из настроек
действует, пока в командной строке нет `--no-rebase`. Прежняя версия движка на строке 2 таблицы
отказывала вместо слияния — исправлено в `integrate` (`remoteCommands.ts`), закреплено тестами.
