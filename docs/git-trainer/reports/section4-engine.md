## Архитектурное решение: что портировано, а что импортировано

«Модель раздела 2» здесь — не только стиль файлов, а буквальное переиспользование уже сверенных с
git алгоритмов `branchRepo.ts`, но БЕЗ изменения этого файла и без попытки подогнать `UndoState`
под тип `BranchingState` фиктивными полями:

- **Импортировано напрямую** (чистые функции над `FileTree`, никакой зависимости от формы
  состояния): `mergeTrees`, `sameTree` из `branchRepo.ts`. Это и есть трёхстороннее слияние
  `git revert` (роли: `base` = дерево отменяемого коммита, `ours` = текущий HEAD, `theirs` =
  дерево родителя отменяемого коммита) — тот же самый, уже сверенный с git 2.53.0 алгоритм, что и
  у `git merge` раздела 2. Совпадение подтверждено отдельным прогоном (см. ниже, «непересекающиеся
  правки»).
- **Портировано** (переписано под `UndoState`, тот же приём, что и `inspectDiff.ts` с LCS
  раздела 2): `checkSafety`/`applyTreeChange` — типизированы в `branchRepo.ts` под
  `BranchingState` (требуют `branchOrder`/`lastMerge`/`missionsDone` раздела 2); подгонять под них
  `UndoState` фиктивными полями было бы нечестным трюком ради избежания дублирования, поэтому
  логика скопирована и адаптирована.
- **Переиспользовано без копии** (реэкспорт готовых, уже сверенных данных о настоящем git):
  `GLOBAL_GIT_OPTIONS`/`REAL_GIT_COMMANDS`/`gitNotACommand` из `branchScope.ts`;
  `classifySection2Option` — для `add`/`commit`/`status`/`branch` (та же команда git даёт те же
  реальные флаги независимо от раздела); `classifySection3Option` — для `log` (тот же приём);
  `applyStageAll`/`buildCommitMessage`/`classifyCommitFlagToken` из `commitFlags.ts`.

## Что сделано по каждому пункту задачи

**1. Исходное состояние** — `createUndoSection(seed)` строит цепочку из трёх коммитов
(«Добавить стили» → «сменить шрифт на Comic Sans» → «Добавить структуру страницы»), дословно из
`source.html`, `ch4.seed` (единственный источник точного состава — spec.md называет только два из
трёх коммитов). Контент — в словаре (`ru.undo.seed`), не в движке.

**2. Команды.**
- `git revert <коммит>` / `HEAD` / `--no-edit` — реализовано, роли трёхстороннего слияния см.
  выше.
- `git reset --soft|--mixed(по умолчанию)|--hard <коммит>` — реализовано, все три режима сверены
  напрямую.
- `git reset [<коммит>] [--] <файл>...` / `git reset HEAD <файл>` — реализовано (обратная
  операция к `git add`), включая честную разницу «с явным `--`, любой путь принимается молча» vs
  «без `--`, единственный нераспознанный токен — настоящая ошибка git» (см. ниже).
- Ошибки из таблицы: `git reset --hard <файл>` (`Cannot do hard reset with paths.`), неизвестная
  ссылка (`ambiguous argument`/`bad revision`), `git revert` без аргумента (usage-блок).
- Дополнительно (не тема раздела, но нужно для реальной игры терминалом): `git add`, `git commit`,
  `git status`, `git log` (голый + `--oneline` — искать хэш), `git branch` (список + создание,
  нужно для `git branch rescue <хэш>`, target.md, часть VI, опасное место 4).

**3. Что НЕ входит — по правилу области.** Конфликт при revert (`CONFLICT`, `--abort`,
`--continue`, `--skip`, `--quit`) — обнаруживается (тем же алгоритмом, что и merge раздела 2), но
не разрешается: честный отказ трейнера, без выдуманных `<<<<<<<`-маркеров. `-n`/`--no-commit`,
`-m`/`--mainline` у revert; `-q`/`--quiet`, `--merge`, `--keep` у reset — все реальные, но
названные вне области. `git reflog`/`git restore` — реальные команды, не реализованные здесь.

**4. Недостижимые коммиты.** `getOrphanCommits(state)` — коммиты, не достижимые ни из одной ветки
(BFS/DFS от всех вершин `state.branches`), отдельным списком; коммиты никогда не удаляются из
`state.commits` (как и у настоящего git — объект коммита не удаляется `reset`'ом). После
`git branch <имя> <хэш>` коммит снова входит в достижимое множество — список пустеет.

**5. Четыре миссии по событию** — тексты и проверки дословно из `source.html`, `ch4.missions`.

## Тексты, сверенные с git (git 2.53.0, mktemp-каталог, 26.09.2026)

- `git revert --no-edit <коммит>` — `[<ветка> <hash>] Revert "<сообщение>"`. Настоящий git ещё
  печатает строку `Date:` и диффстат (`N file(s) changed…`, `delete mode…`) — у тренажёра нет
  настоящей даты (target.md, часть II, A5) и он не считает диффстат (то же осознанное упрощение,
  что уже принято в `branchCommands.ts` для обычного `commit`/`merge`, см. её шапку) — обе строки
  просто не печатаются, а не подделываются.
- **`git revert` повторно (нечего отменять) — расхождение с `source.html`/`spec.md` (S4-03).**
  Оба ожидали свой текст «нечего отменять: изменения коммита … уже отменены». Реальный git 2.53.0
  в этом случае вообще не печатает специальный текст: он просто идёт по тому же пути, что и
  `git commit` без реальных изменений, и печатает ОБЫЧНЫЙ `git status`, завершаясь отказом
  (`On branch <ветка>\n\nnothing to commit, working tree clean`, код 1). Реализовано так, как
  сверено, а не так, как ожидал spec — `formatUndoStatus`.
- **Двухуровневая проверка «было бы затёрто» у revert — важный нюанс, не описанный в
  source.html/spec.md.** Реальный git проверяет ДВЕ разные вещи по отдельности:
  1. Индекс отличается от HEAD ГДЕ УГОДНО (даже в файле, которого revert не касается) → короткое
     сообщение `error: your local changes would be overwritten by revert.\nhint: commit your
     changes or stash them to proceed.\nfatal: revert failed` — приоритет НАД проверкой «нечего
     отменять» (staged-правка в совсем другом файле блокирует revert, даже когда сам revert
     результата бы не поменял).
  2. Только если (1) не сработала — файл, который revert реально трогает, отличается в рабочем
     дереве от индекса → **другое** сообщение, буквально то же самое, что у `git merge`:
     `error: Your local changes to the following files would be overwritten by merge:\n\t<файл>
     \nPlease commit your changes or stash them before you merge.\nAborting\nfatal: revert
     failed`. Слово `merge` в тексте для `revert` — не опечатка source.html и не наша, это
     реальный git так печатает (сверено дважды, разными сценариями).
- `git revert` без аргумента / с любым нераспознанным флагом (фейковым или реальным, но не
  входящим в `[--[no-]edit] [-n] [-m …] [-s] [-S…]`) — настоящий git печатает ОДИН И ТОТ ЖЕ
  24-строчный usage-блок без вводной строки `error:` (сверено: `git revert`, `git revert --bogus`,
  `git revert -s` без коммита и `git revert --bogus HEAD` дают дословно идентичный вывод).
  Раздел не пытается различать «фейковый» и «реальный, но не в области» флаг там, где сам git их
  не различает — честнее воспроизвести один и тот же блок, чем выдумать несуществующее различие.
- `git reset --soft|--mixed|--hard <коммит>` — все три формы вывода (`''`/`Unstaged changes after
  reset:\nM\t<файл>`/`HEAD is now at <hash> <сообщение>`) сверены напрямую, включая то, что
  «неотслеживаемые» файлы `reset --hard` не трогает.
- `git reset [<коммит>] [--] <файл>` — сверено: с явным `--` ЛЮБОЙ путь принимается молча, даже
  несуществующий (`git reset -- nosuchfile` → код 0, пусто) — pathspec не валидируется вовсе.
  Без `--` — только ПЕРВЫЙ позиционный токен проверяется («это ссылка или известный путь?»);
  если нет — `fatal: ambiguous argument '<x>': unknown revision or path not in the working
  tree...`; если да — ВСЕ токены становятся путями без дальнейшей проверки (`git reset a b` с
  несуществующим `b` проходит молча). `git reset badref -- <файл>` (явный `--`, но ссылка перед
  ним не резолвится) — ОТДЕЛЬНОЕ сообщение `fatal: Failed to resolve 'badref' as a valid tree.`
  (не «ambiguous argument»).
- `git reset --hard/--soft <файл>` (известный путь, не ссылка) — `fatal: Cannot do
  {hard|soft} reset with paths.` — но ТОЛЬКО когда токен реально известен git; для неизвестного
  токена в любом режиме — `ambiguous argument`, а не «Cannot do…».
- `git reset --bogus`/`-Z` — `error: unknown option \`bogus'`/`error: unknown switch \`Z'` + тот
  же 26-строчный usage-блок, что и на голый `git reset -h` (без строки `error:`).
- **`git status`: важная поправка к уже принятому в разделе 2/3 формату (см. «Открытые
  вопросы»).** Прогон в полностью изолированном `HOME` (без пользовательских `~/.gitconfig`)
  показал, что при непустом `staged` настоящий git заканчивает вывод ПУСТОЙ СТРОКОЙ — то есть
  двумя `\n` подряд после последней содержательной строки, а не одним. Формула
  `formatBranchingStatus`/`formatInspectStdatus` (`branchRepo.ts`/`inspectRepo.ts`, разделы 2–3,
  строка `if (s.staged.length) output += '\n'`) добавляет только ОДИН `\n` — на один символ
  меньше, чем показал мой прогон (byte-diff подтверждён трижды, разными сценариями: только
  staged; staged+untracked). `formatUndoStatus` (раздел 4) написан с `output += '\n\n'` —
  по СВОЕЙ прямой проверке. Секции 2/3 не трогались (не моя область) — см. открытый вопрос ниже,
  это стоит перепроверить и, возможно, поправить отдельно (правило CLAUDE.md про «общий код
  разделов» не применяется впрямую: сама функция не общая, а независимая копия в каждом разделе,
  но ЕСЛИ разница подтвердится ещё раз — это один и тот же баг в трёх местах).
- `git branch <имя> <хэш>` (создание, включая `rescue`) — `fatal: a branch named '<x>' already
  exists`, `fatal: not a valid object name: '<x>'` — тексты те же, что уже сверены и используются в
  `branchCommands.ts` (переиспользованы как готовые литералы, не импорт кода).

## Список упрощений (для ревью)

1. **`resolveRef` не разбирает выражения ревизий `HEAD^`, `@`, `HEAD@{n}`** — как и в разделе 2
   (target.md, часть IV, «Что НЕ входит»). `looksLikeUnimplementedRevisionExpression` отличает
   этот случай от genuinely неизвестной ссылки: честный отказ по правилу области
   (`ue.optionOutOfScope`), а не «bad revision»/«ambiguous argument».
2. **Неоднозначный короткий хэш** (несколько коммитов с общим префиксом) трактуется как «не
   найдено» (`null`), без отдельного сообщения git про неоднозначность — тот же принцип, что и в
   разделе 3 (`inspectRepo.ts`), риск коллизии на 3–5 коммитах и 7-значном хэше принят.
3. **`git log` раздела 4 — только голая форма и `--oneline`.** Полный разбор (`-n`, диапазоны,
   `<файл>`, флаги вывода) — тема раздела 3 (`inspectCommands.ts`); здесь `log` нужен только
   чтобы найти хэш для `revert`/`reset`, поэтому набор сознательно минимальный. Любой другой
   реальный флаг `log` (не `--oneline`) корректно распознаётся как «реальный, здесь не
   разбирается» через переиспользование `classifySection3Option`, но не РЕАЛИЗУЕТСЯ.
4. **`git branch` раздела 4 — только создание (с опциональной начальной точкой) и список.** Ни
   переключения (`checkout`), ни удаления, ни `-m`/`-d` — раздел 4 никогда не переключает HEAD
   (него нет в «Что входит»), вторая ветка нужна только чтобы «спасти» отброшенный коммит.
   Собственная, не разбирающая сокращения/кластеры классификация имён — как в `handleBranch`
   раздела 2, но без формы `<имя> <несколько аргументов>` (той же ошибкой, что уже даёт раздел 2).
5. **`checkSafety`/`applyTreeChange` портированы, а не импортированы** (см. «Архитектурное
   решение» выше) — сознательный выбор в пользу не подгонять `UndoState` под `BranchingState`
   фиктивными полями ради частичного избежания копирования 2 функций (~50 строк).
6. **Разбор позиционных токенов `git reset` без `--`** — только ПЕРВЫЙ токен решает «ссылка или
   путь»; коллизия «токен одновременно и валидная ссылка, и известный путь» не разбирается
   отдельно (в сценариях раздела имена файлов — `style.css`/`index.html` — никогда не совпадают
   с именами веток/хэшами, риск не реализовался ни разу за время сверки).
7. **Диффстат/`Date:` после успешного revert не печатаются** — то же решение, что уже принято
   для `commit`/`merge` раздела 2 (см. шапку `branchCommands.ts`): «либо дословно, либо явно не
   разбирать», не наполовину придуманный вывод.
8. **`git commit`/`git add`/`git status` раздела 4 — тот же минимальный набор, что и у раздела 2**
   (без pathspec-коммита, без `-A`/`*`-глоббинга `git add` уровня раздела 1) — сознательно не
   расширялся, это не тема этого раздела.

## Открытые вопросы к интегратору/ревьюеру

- **Возможная ошибка на 1 символ в `formatBranchingStatus`/`formatInspectStatus`** (разделы 2/3,
  файлы `branchRepo.ts`/`inspectRepo.ts`) — см. раздел «Тексты, сверенные с git» выше. Я не трогал
  эти файлы (не моя область), но прогон именно СЕЙЧАС, именно на этой машине (git 2.53.0,
  изолированный `HOME`), трижды воспроизвёл лишний `\n` в конце вывода `git status`, когда
  `staged` не пуст, по сравнению с тем, что фиксируют уже принятые тесты `branchCommands.test.ts`.
  Стоит перепрогнать независимо (другой машиной/датой) и, если подтвердится, поправить один раз
  в обоих местах (это как раз «общий код разделов» по духу правила CLAUDE.md, хоть и не в одном
  файле) — я исправил только СВОЮ независимую копию (`undoRepo.ts`, `formatUndoStatus`) по итогам
  своей проверки.
- **`git revert -m 1 HEAD`** (не конфликт, реальный флаг) — попадает в общий «конфликтный»
  бакет вместе с `-n`? Нет — у него отдельное сообщение (`revertMainlineOutOfScope`), не
  конфликтное; проверено тестом. Уточнить у ревьюера, не нужно ли развести формулировки ещё
  тоньше (`-m` без числового значения и т.п.) — сейчас любое написание `-m`/`--mainline`
  (в т.ч. `--mainline=2`) получает один и тот же текст.
- **Правка, затрагивающая revert, но не влияющая на итоговое содержимое** (застейдженная правка
  СЛУЧАЙНО совпавшая с целевым результатом) — как и `checkSafety` раздела 2, не блокируется (то
  же поведение, что уже сверено и принято для checkout/merge раздела 2) — отдельно для revert не
  перепроверялось, полагаюсь на идентичность портированного алгоритма.
