> Этот файл описывает поведение исходного тренажёра `docs/git-trainer/source.html` по состоянию на 19.09.2026, включая его ошибки; он не описывает текущий код; где расходится с `target.md`, верен `target.md`.

Спецификация извлечена из тестовых наборов p1_5, p2_5, p3, p5, p6, p7, p10–p15, ui_p5, p6_ch8, p6_ch8b и audit. Она описывает, что должно происходить, без привязки к селекторам и разметке: любая реализация, которая проходит эти проверки, ведёт себя как эталон.

## Как читать

Каждая проверка записана в виде «исходное состояние → действие → ожидаемый результат». В конце строки в квадратных скобках указан набор, из которого она взята.

Условные обозначения:

- **Команда** — строка, введённая в терминал раздела с нажатием Enter.
- **Правка файла** — нажатие кнопки «✎ изменить» рядом с файлом в панели файлов (если не сказано, какой файл, правится первый в списке).
- **💡** — пояснение, которое тренажёр печатает под выводом команды. Приведённые в кавычках фрагменты должны присутствовать в тексте пояснения.
- **Отказ** — команда завершается ошибкой: вывод показан как ошибка, состояние репозитория не меняется, если не сказано иное.
- **Миссии** — список «Что попробовать» раздела; миссия «засчитана», когда помечена выполненной.
- **Чистое дерево** — в рабочем каталоге нет несохранённых правок.
- Фрагменты в кавычках внутри «Ожидаемо» — реальные сообщения Git (или их аналог), которые тренажёр обязан выдавать дословно.
- **по коду** в столбце «Набор»/«Источник» — пункт восстановлен чтением `git-trenazher_15.html` и сверен запуском страницы; в сохранённых наборах такой проверки нет или она проверяла другое. Такие пункты надёжнее строк «p…», где проверка могла быть слабой (см. раздел 11).

Сокращение: `ok` — команда выполнена без ошибки. Раздел 8 — «Приложение: пять важных тем».

### 2.1. Что делает раздел 1 особенным (режим «friendly»)

У раздела 1 включён флаг `friendly`. Остальные разделы используют тот же движок команд, но без этого флага. Различия:

| Область | Раздел 1 (friendly) | Разделы 2–8 |
|---|---|---|
| Умные кавычки | `“ ” „ « »` в введённой строке заменяются на обычные `"` до разбора | Не заменяются |
| Команда `git` без аргументов | `ok`, вывод «usage: git <команда> [<аргументы>]\nГлавное для этого раздела: init, status, add, commit» | Не обрабатывается отдельно |
| `git --version`, `git version` | `ok`, «git version (учебный тренажёр — реальная версия зависит от твоей установки)» | Не обрабатывается отдельно |
| Повторный `git init` | `ok` (не красная ошибка): «Reinitialized existing Git repository in site/.git/» | Отказ (красный вывод) с тем же текстом |
| Вывод `git status` | Как в настоящем Git: пустые строки между блоками, подсказки в скобках, «No commits yet», итоговая строка (см. 2.4) | Сокращённый: без пустых строк и подсказок |

### 2.4. `git status` в разделе 1

Формат вывода (`git status`), блоки печатаются в таком порядке:

1. Первая строка: «On branch <имя>» или «HEAD detached at <7 символов хэша>».
2. Если коммитов нет: пустая строка и «No commits yet».
3. Если есть подготовленные файлы: пустая строка, «Changes to be committed:», затем строки вида «\t<тип>:\t<файл>» с типами `new file`, `modified`, `deleted`.
4. Если есть изменённые, но не подготовленные: пустая строка, «Changes not staged for commit:», подсказка «  (use "git add <file>..." to update what will be committed)», затем строки «\tmodified:\t<файл>» или «\tdeleted:\t<файл>».
5. Если есть неотслеживаемые: пустая строка, «Untracked files:», подсказка «  (use "git add <file>..." to include in what will be committed)», затем строки «\t<файл>».
6. Пустая строка и **итоговая строка**, но только если нет подготовленных файлов: при наличии неподготовленных правок — «no changes added to commit (use "git add" and/or "git commit -a")»; иначе при наличии неотслеживаемых — «nothing added to commit but untracked files present (use "git add" to track)»; иначе при отсутствии коммитов — «nothing to commit (create/copy files and use "git add" to track)»; иначе — «nothing to commit, working tree clean». Завершающие пустые строки обрезаются.

Внутри каждого блока файлы идут в порядке появления в объединённом наборе (файлы HEAD, затем индекс, затем рабочий каталог), а не по алфавиту; в коротком формате `-s` — по алфавиту.

### 11.3. Что спецификация не покрывает

- **Раздел 1.** Полное поведение восстановлено чтением кода (раздел 2 спецификации), но автоматических тестов на него в сохранённых наборах по-прежнему нет: строки S1-10…S1-128 не подкреплены скриптом, а только разовой ручной сверкой запуском. Их стоит превратить в набор `p1.py`.
- **Контраст.** `audit.py` смотрит только текстовые узлы в неизменённом состоянии разделов и в состоянии после первых трёх ответов квиза. Не охвачены: состояния после выполнения команд (конфликт-рамка, бейджи статуса после действий, ход bisect), подписи в SVG-графе (у них цвет задаётся заливкой, а не свойством цвета текста), наведение (hover).
- **Клавиатура.** Проверены Enter на строке blame и стрелки в терминале. Табуляция, доступность кнопок квиза и переключателей с клавиатуры не проверялись.
- **Размеры окна.** Только 1280×900 и 375/390 px. Планшетная ширина (около 760–900 px, где меняются брейкпоинты раскладки) не проверялась.
- **Расстояние до терминала на телефоне.** Проверяется только порядок «терминал выше панелей», но не то, как далеко он от верха страницы: в разделе 2 на 375 px он находится примерно в 2900 px от верха после шапки, списка разделов, теории и миссий.
- **Содержательная проверка теории.** Проверяются отдельные фразы, а не полнота и точность текста.
- **Хранилище.** Проверяется только ключ прогресса `git-trenazher-progress-v1`: несколько вкладок и миграция со старых форматов не проверялись.

### 11.4. Особенности запуска, влияющие на воспроизводимость

- Запросы к серверам шрифтов Google блокируются, поэтому вёрстка измеряется на запасных шрифтах.
- Часть проверок читает состояние напрямую (`STATE`, `STATE_DEFS`, `CHAPTERS`, методы `GitRepo`, например `_resolveRef`) и потому привязана к внутренним именам; в этой спецификации такие проверки записаны как наблюдаемое поведение (например S3-41…S3-43), но в коде наборов они выполняются через внутренние объекты.
- Порядок команд внутри сценариев важен: многие проверки опираются на состояние, оставленное предыдущей проверкой той же страницы (например, разделы S2-50…S2-60 идут подряд на одной странице). Свежая страница для каждой проверки в наборах создаётся не везде.

### 11.5. Расхождения, замеченные при чтении кода

Это не проверки, а наблюдения: места, где текст или поведение не согласуются между собой. Ни одно из них не исправлялось.

- **Ссылка на несуществующий список.** Для настоящих, но неподдерживаемых команд (`git grep`, `git help` и т. п.) выводится подсказка «попробуй то, что есть в списке быстрых команд под терминалом». Кнопки быстрых команд отключены намеренно (функция, которая их рисует, возвращает пустую строку), поэтому такого списка на экране нет. Поле `quickCmds` у разделов остаётся неиспользуемыми данными.
- **Жёстко прописанное имя файла в подсказке.** Пояснение к отказу `git commit` («Сначала добавь файл: git add index.html…») всегда называет `index.html`, даже если единственный файл удалён или добавлять нужно другой.
- **Пояснение про кавычки срабатывает шире, чем нужно.** Любой отказ `git commit` со словом «pathspec» получает подсказку про кавычки, в том числе `git commit nosuch -m x`, где кавычки ни при чём.
- **Повторный `git init`.** В разделе 1 это `ok`, в разделах 2–8 — красная ошибка с тем же текстом «Reinitialized existing Git repository…» и без пояснения.
- **Надпись «заголовок короткий» рядом с ℹ про длину.** Для многословного заголовка длиной 51–72 символа проверка сообщения одновременно выводит «✓ … заголовок короткий…» и «ℹ заголовок N символов — принято укладываться примерно в 50».
- **Панель статуса без коммитов и без файлов.** Если в разделе 1 удалить единственный файл до первого коммита, панель пишет «Рабочий каталог чист — можно спокойно переключать ветки.», а `git status` — «No commits yet… nothing to commit (create/copy files…)».
- **Тихие отказы в терминале алиасов.** Чтение или `--unset` несуществующего алиаса возвращает `ok = false` с пустым выводом: пользователь видит только красную пустую строку.
- **Миссии считаются по-разному.** В разделах 1 и 8 миссия пересчитывается по текущему состоянию и истории (может «слететь», например при удалении тега или `git rm`), в разделе 7 запоминается и не снимается.
